# KeysDock Hardware Architecture

## Scope

This document reviews the hardware only.

- Firmware and software in this repository are still demo-stage placeholders.
- `suitekits/` contains 3D and enclosure assets and is intentionally excluded here.
- Source of truth for this review is the KiCad data under `hardware/` and the datasheets under `hardware/docs/`.

## Board Set

| Board | Role | Main Devices | Main Interfaces |

## Top-Level Architecture

KeysDock is split into one active controller board and one large sensing board.

- The controller board owns USB, battery charging, system power conversion, the ESP32-C6, the external SPI ADC, and the rotary encoder.
- The typeboard carries the main 64 hall-effect switches and the RGB chain.
- The external board adds 14 more hall-effect keys through a pogo-connected analog expansion path.
- The connector board is electrically simple and exists only to bridge mechanical placement between the controller and the typeboard.

## Power Architecture

### Observed rail tree

The current power tree is:

`USB-C VBUS -> USB_PWR_SUPP -> BQ24074 U2 -> P,+5 -> TPS62142 U6 -> P,+3.3`

Battery input is on `VBAT` through `J3`, and the BQ24074 power-path stage can backfeed the system output from the battery when external input is absent.

### Important consequence: `P,+5` is not a true 5V rail

The net is named `P,+5`, but electrically it is the BQ24074 `OUT` rail:

- about 4.4V when external input is present,
- about battery voltage when external input is absent.

That means the RGB rail is really a variable system rail, not a regulated 5V bus.

### Charger configuration as currently wired

From the installed resistor values and pin straps on `U2`:

- `R7 = 1.78k` programs about 500mA charge current.
- `R8 = 1.54k` programs about 1.0A input current limit.
- `R11 = 3k` programs about 50mA termination current.
- `~CE` is tied low, so charging is always enabled when input is valid.
- `EN2` is high and `EN1` is low, so the charger runs in resistor-programmed current-limit mode.
- `TMR` is tied low, so safety timers are disabled.
- `TS` is strapped to ground through a fixed resistor, so pack NTC monitoring is effectively disabled.

### 3.3V domain feasibility

The 3.3V rail is generated by the TPS62142 buck and is fundamentally compatible with the rest of the design:

- ESP32-C6 logic is 3.3V.
- TLA2518 AVDD and DVDD are both tied to 3.3V.
- SC4823 hall sensors operate from 2.5V to 5.5V and are specified at 3.3V.
- XL4067TS works from 2V to 10V, so 3.3V mux operation is valid.

The 3.3V current budget is also comfortable.

- 78 hall sensors at 0.6mA typical active current are about 46.8mA total.
- 5 muxes contribute very little current.
- TLA2518 is sub-1mA class.
- The ESP32-C6 and future radio workloads dominate the 3.3V dynamic load, but the 2A buck still has good headroom.

## Hall Sensor and ADC Architecture

### Main board scan path

The main typeboard uses four identical 16-key groups.

- Each group contains 16 SC4823 hall sensors.
- Each group feeds one XL4067TS analog mux.
- The four mux outputs become `KEYS_DT_1` through `KEYS_DT_4`.

### External dock scan path

The external dock uses one more XL4067TS.

- 14 SC4823 sensors feed the mux.
- The dock exports one analog output as `KEYS_ADC_OUT`.
- That signal crosses the 8-pin pogo interface and ultimately reaches the controller as the fifth analog return path.

### Controller-side acquisition

The TLA2518 on the controller is wired as follows:

- AIN2..AIN6 read the five keyboard analog return lines.
- AIN7 is currently wired directly to `VBAT`.
- SPI is direct between the ESP32-C6 and the ADC.

### Why the analog architecture is fundamentally sound

The key electrical pairing is reasonable.

- SC4823 output is referenced to the same 3.3V domain used as ADC reference, so the measurement chain is ratiometric.
- SC4823 zero-field output sits near `0.9 * VCC`, and the magnetic travel moves the signal across most of the ADC range.
- XL4067 on-resistance is low enough for this use case, and the TLA2518 acquisition time is fast enough that mux settling is not the primary bottleneck.

In practice, this means the architecture is viable for hall-key scanning without analog buffers, provided supply noise is kept under control.

### Scan-rate headroom

The raw scan math is favorable.

- 16 mux addresses x 5 return lines = 80 analog samples per full keyboard scan.
- TLA2518 supports 1MSPS with 400ns acquisition and 600ns conversion class timing.
- Even after adding SPI overhead, mux switching delay, and moderate averaging, scan rates well above normal keyboard requirements are still achievable.

### Shared sleep and wake signals

The main board exposes two useful group-wide control lines:

- `RANA` appears to be the shared hall sleep control path.
- `SAKI_MOVE` appears to be the shared hall wake/activity indication path.

This is a strong design choice for future low-power firmware on the main 64-key board.

The external dock intentionally does not carry the same sleep/wake behavior.

## Interconnect Architecture

### Controller to typeboard

The 20-pin board-to-board link carries:

- 2 x `P,+5`
- 2 x `P,+3.3`
- 3 x common return
- 5 analog return / mux-control signals
- `TOMO0` LED data
- `RANA`
- `SAKI_MOVE`

This pin budget is logically correct for the current system partition.

### Typeboard to external dock

The 8-pin pogo link carries:

- `KEYS_CH_A`
- `KEYS_CH_B`
- `KEYS_CH_C`
- `KEYS_CH_D`
- `KEYS_CH_CE`
- external analog return
- `P,+3.3`
- return

This is also a sensible minimum interface for a hall-sensor-only expansion board.

## Grounding Strategy

The design does not use a single simple ground net.

- `P,E` is the common inter-board return exported across the connector system.
- `P,GND` is a local ground domain used around sensitive circuitry on multiple boards.
- Local 0 ohm bridges connect them:
  - controller: `R10`
  - typeboard: `R1`
  - external: `R4`

This can work, but it is also the highest noise-risk part of the current analog design.

The specific concern is that hall sensors, LEDs, ADC, and pogo returns do not all live on the exact same ground copper at all times. If LED return current or connector current builds a measurable offset across the 0 ohm bridge or across local copper, the ADC sees that as key-position noise.

The pogo interface is the clearest example:

- the typeboard exports pogo ground on local `P,GND`,
- the external board receives pogo ground on local `P,E`,
- both ends rely on the local 0 ohm bridge being fitted and quiet.

That is acceptable for bring-up, but it is not the cleanest possible analog return strategy.

## PCB Electrical Characteristics

### Common stackup

All reviewed boards use a 4-layer, 1.2mm stackup.

- `F.Cu`
- `In1.Cu`
- `In2.Cu`
- `B.Cu`

This is a good baseline for mixed-signal keyboard hardware.

### Controller routing

The controller PCB is the strongest electrical board in the set.

- USB D+ and D- are short, closely matched, and referenced by an internal return plane, which is good enough for Full-Speed USB.
- The ADC sits close to the 20-pin board-to-board connector, so the five analog return lines stay short on the controller board.
- Charger, buck, and ADC decoupling are present locally.

### Typeboard routing

The typeboard uses a strong architectural placement strategy.

- Hall sensors are partitioned into local 16-key groups.
- Each group has its own local mux, so long raw analog traces are avoided.
- The 5V and 3.3V trunks are mostly carried on wider internal routing instead of thin surface-only serpentine traces.

The biggest weakness is supply integrity, not raw routing geometry.

### External board routing

The external board is also logically well partitioned.

- One local mux near the 14 hall sensors keeps the external analog path short.
- Only one analog output has to cross the pogo link.

Again, the main weakness is missing local supply support.

### Connector board routing

The connector board is electrically simple and low risk in logic terms, but it is likely the narrowest power bottleneck in the whole system.

- It uses thin signal-width routing even for the `P,+5` and `P,+3.3` lines.
- This is probably fine for logic and sensor current.
- It is much less comfortable for the RGB rail under aggressive brightness.

## Board-by-Board Review

### Controller board

Strengths:

- coherent ESP32-C6 / SPI ADC / hall mux logic chain,
- short ADC input paths,
- plausible USB routing,
- local power circuitry and decoupling present,
- encoder and charger status already exposed to the MCU.

Risks:

- `VBAT` is wired directly into TLA2518 AIN7 with no divider, which exceeds the ADC input range whenever battery voltage rises above AVDD.
- USB front end does not show obvious ESD protection or input fuse/load-switch protection.
- USB-C CC pulldowns are 4.7k, while 5.1k is the standard sink value.
- BQ24074 safety timers are disabled.
- Battery temperature monitoring is disabled.
- `~PGOOD` from the charger is left unused.

### Typeboard

Strengths:

- clean 64-key partition into 4 local mux groups,
- short local analog fan-in,
- reasonable 20-pin interface usage,
- shared low-power control hooks already routed.

Risks:

- no explicit decoupling capacitors are placed on the board,
- no visible bulk capacitor at the 5V entry despite 65 RGB devices,
- LEDs and hall sensors share local return copper through the `P,E` domain,
- variable `P,+5` rail means LED behavior depends heavily on source state and battery voltage.

### Connector board

Strengths:

- passive only,
- low logical complexity,
- easy to validate with continuity and voltage-drop tests.

Risks:

- 0.3mm class power routing should be rechecked against RGB current draw and connector current rating.

### External board

Strengths:

- simple local mux expansion,
- no unnecessary RGB load,
- minimal pogo signal set.

Risks:

- no explicit decoupling capacitors,
- ground/reference continuity depends on the local 0 ohm bridge,
- no sleep/wake path, so it is an always-on analog extension unless firmware cuts board power elsewhere.

## Power-Budget Reality Check

The hall-sensor side is easy to power. The LED side is not.

### Hall and control side

- 78 hall sensors x 0.6mA typical active current = about 46.8mA.
- 5 muxes add very little.
- TLA2518 adds very little.
- The 3.3V buck therefore has comfortable headroom for the sensing subsystem.

### RGB side

The keyboard has 66 WS2812-compatible LEDs total.

The referenced LED datasheet is a 24-bit GRB device with 12mA nominal per color channel, so a simple worst-case estimate is:

- `66 x 3 x 12mA = 2.376A`

That is the real system-level constraint.

- The charger input is configured for about 1.0A maximum input current.
- The exported LED rail is not a true fixed 5V source.
- Full-white, full-brightness operation cannot be treated as a sustainable USB-powered operating point.

The hardware can still work well if firmware enforces a power-aware lighting policy.

## Overall Feasibility Verdict

The system architecture is fundamentally workable.

What already looks good:

- ESP32-C6, TLA2518, XL4067TS, and SC4823 are electrically compatible.
- The distributed mux strategy is appropriate for a hall keyboard.
- Controller USB routing is plausible.
- The 3.3V sensing domain has enough current margin.

What currently blocks production confidence:

- direct `VBAT` to ADC overvoltage,
- missing decoupling on typeboard and external,
- disabled charger timers and disabled battery NTC monitoring,
- LED power rail naming and budgeting mismatch,
- weak USB protection,
- ground-domain complexity that is not yet clearly justified by measured results.

In short: the design is feasible for bring-up and likely can be made functional, but it is not yet production-ready without at least one corrective hardware revision.

## ESP32-C6 Controller Pin Review

The controller pin map is mostly sensible, but a few pins need explicit hardware biasing before the design can be considered robust.

| Pin | Net | Current role | Verdict | Hardware notes |
| --- | --- | --- | --- | --- |
| `CHIP_PU` | `EN` | chip enable / reset | must fix | Espressif explicitly says not to leave this pin floating. Add an external pull-up and RC reset network. |
| `GPIO0` | `WHEEL_A` | encoder input | good | External `10k` pull-up already present. LP-domain pin, so it can also participate in wake strategies later. |
| `GPIO1` | `WHEEL_B` | encoder input | good | External `10k` pull-up already present. Same low-power flexibility as `GPIO0`. |
| `GPIO2` | `SPI_MISO` | ADC SPI data in | good | No strap conflict. LP-domain pin but used in a normal active-mode SPI role. |
| `GPIO3` | `SAKI_MOVE` | hall wake/activity input | must fix bias | This is a strong deep-sleep wake candidate because it is in the `VDDPST1` / LP domain. The net currently has no visible pull-up on the controller side. |
| `GPIO5 / MTDI` | `BAT_CHG` | charger status input | must fix | `CHG` from `BQ24074` is open-drain and needs a pull-up. This pin is also a strapping pin, so leaving it undefined at reset is poor practice. |
| `GPIO6` | `SPI_CLK` | ADC SPI clock | good | Normal digital output usage. No boot-mode conflict identified. |
| `GPIO7` | `SPI_MOSI` | ADC SPI data out | good | Normal digital output usage. No boot-mode conflict identified. |
| `GPIO8` | `BOOT_1` | boot strap helper | should fix | This is a boot-mode strapping pin and is currently floating. Add a defined bias that matches the intended download-mode entry method. |
| `GPIO9` | `BOOT_0` | boot strap button | should fix | This is the main boot-mode strap. Internal weak pull-up exists, but Espressif recommends an external pull-up and warns against large capacitors here. |
| `GPIO10` | `KEYS_CH_A` | mux address | good | Straightforward output role. |
| `GPIO11` | `KEYS_CH_B` | mux address | good | Straightforward output role. |
| `GPIO12` | `USB_D-` | native USB D- | good with cleanup | Correct native USB pin. Add the recommended small series resistor and USB ESD protection. |
| `GPIO13` | `USB_D+` | native USB D+ | good with cleanup | Correct native USB pin. Same series resistor and ESD comments as `GPIO12`. |
| `GPIO15` | `KEYS_CH_C` | mux address | acceptable with caution | This is a strapping pin related to early JTAG source selection. It is usable here under default eFuse assumptions, but it should not be loaded by anything that can create undefined reset levels. |
| `GPIO16` | `U0TX` | UART log / download TX | good | Useful bring-up path and does not conflict with the current design. |
| `GPIO17` | `U0RX` | UART log / download RX | good | Useful bring-up path and does not conflict with the current design. |
| `GPIO18` | `KEYS_CH_D` | mux address | good | Straightforward output role. |
| `GPIO19` | `SPI_CS3_ADC` | ADC chip select | good | Clean dedicated control line. |
| `GPIO20` | `SPI_CS4_EINK` | future E-ink chip select | good | Fine as a spare peripheral select. |
| `GPIO21` | `RANA` | hall sleep control | usable with firmware hold | This net can control main-board hall sleep, but `GPIO21` is not in the LP domain. Deep-sleep behavior therefore depends on setting the output level before sleep and enabling GPIO hold. |
| `GPIO22` | local LED then `TOMO0` | RGB data source | good | The signal first enters the controller-board LED and then continues to the typeboard chain. No conflict found. |
| `GPIO23` | `KEYS_CH_CE` | mux enable | good | Straightforward output role. |

### Boot and download implications

- `GPIO8` and `GPIO9` are the boot-mode strapping pins for `SPI boot` versus `Joint Download Boot`.
- `GPIO9` defaults high internally, which is why normal boot can still work today.
- `GPIO8` is currently floating, so the hardware download path is not deterministic.
- If the intent is to keep a single manual boot button, the cleanest direction is to give both straps defined default levels and let the button pull `GPIO9` low for download entry.
- This matters even though ESP32-C6 supports USB download, because Espressif notes that USB auto-download can stop being available once application firmware repurposes the USB block or USB pins.

### Main-board hall sleep and wake wiring

- `RANA` is confirmed on the typeboard as the shared `HE_SLEEP` input to all 64 main-board hall sensors.
- `SAKI_MOVE` is confirmed on the typeboard as the shared `HE_AWAKE` output from those same sensors.
- The external dock uses the same hall pins very differently:
  - its `HE_AWAKE` bus is pulled up with `10k`, which strongly suggests a wire-OR style activity signal,
  - its `HE_SLEEP` bus is hard-strapped low through `100R`, which means the dock is intentionally fixed in the active state.
- That comparison strongly suggests the controller board should also define default levels on `RANA` and `SAKI_MOVE`, instead of leaving both nets to firmware-only startup behavior.

## State-by-State Feasibility

### Active, USB-powered

- The board should be able to run as a wired USB keyboard once reset biasing is fixed.
- Native USB pin usage is correct.
- The remaining blockers are not architectural; they are reliability issues around reset, strap, and protection.

### Active, battery-powered / wireless

- The controller power path is compatible with battery-only operation.
- Hall scanning, ADC, and the ESP32-C6 itself are all compatible with the 3.3V rail.
- The practical constraint remains RGB current, because the exported LED rail is the charger SYS output rather than a true regulated 5V rail.

### USB / battery switchover

- The BQ24074 power-path architecture is appropriate for wired / wireless switching.
- However, the MCU currently sees `CHG` but not `PGOOD`, so firmware cannot reliably distinguish `USB present but not charging` from `USB absent` using the present signals alone.

### Main-board sleep / wake

- The main-board low-power concept is real and usable.
- `GPIO3` is an LP-domain GPIO, so `SAKI_MOVE` is placed on a pin that can be used as a deep-sleep wake source.
- `GPIO21` is not an LP-domain pin, so `RANA` cannot be actively toggled during deep-sleep by the LP domain; instead, firmware must set the desired level before sleep and enable GPIO hold.
- This means the current main board can support deep-sleep and wake, but only after the `RANA` and `SAKI_MOVE` default-state hardware is cleaned up.

### External-dock sleep / wake

- The external dock does not export an equivalent sleep or wake signal back to the controller.
- Its hall sensors are effectively configured as always-on analog sources.
- Therefore, the external dock is compatible with active scanning, but it is not a peer in the main-board deep-sleep strategy.

## Future Firmware Development Plan

The future firmware should be planned around the actual hardware constraints, not around the current demo code.

### Phase 1: board bring-up

- verify clocks, USB, and logging on ESP32-C6,
- read charger `~CHG`, battery rail state, and dock power rails,
- bring up SPI to TLA2518,
- validate rotary encoder `WHEEL_A` / `WHEEL_B`,
- keep RGB disabled until power budgeting is implemented.

### Phase 2: scan engine

- drive `KEYS_CH_A..D` and `KEYS_CH_CE`,
- scan `KEYS_DT_1..5` through TLA2518,
- use ADC calibration and modest oversampling,
- build per-key baseline capture, hysteresis, and travel filtering,
- support 64 main keys first, then the 14-key external dock.

### Phase 3: low-power behavior

- use `RANA` and `SAKI_MOVE` for main-board sleep/wake,
- treat the external dock as always-on unless later hardware changes add equivalent control,
- add battery-based RGB dim/off policy,
- add source-aware charge and lighting policy.

### Phase 4: transport and features

- USB HID first,
- BLE after scan stability is proven,
- battery and charger telemetry,
- rotary encoder events,
- lighting engine with current limiting,
- firmware update path.

### Phase 5: factory support

- per-key calibration workflow,
- key noise floor test,
- ADC health test,
- connector / external dock presence test,
- battery and charger validation.

## Future Software Development Plan

The companion software should be built as a hardware configuration and diagnostics tool first.

### Recommended order

1. Define a stable device protocol.
   - capability reporting
   - per-key calibration data
   - lighting and power policy settings
   - battery and charger telemetry

2. Build a configuration surface around hardware realities.
   - hall calibration and actuation curves
   - keymap and layer settings
   - encoder behavior
   - external dock enable / disable policy

3. Add diagnostics before cosmetics.
   - live analog graph per key group
   - battery voltage and charger state
   - RGB current policy state
   - transport latency and error logs

4. Add update and manufacturing features.
   - firmware update
   - profile export / import
   - factory self-test report

### Software behaviors that should exist because of current hardware limits

- a global RGB current limiter,
- battery-low lighting cutoff,
- source-aware lighting presets,
- calibration persistence per board and per external dock profile,
- a clear warning if battery telemetry is unavailable on early hardware without a safe divider.
